# I-ITSM · Intelligent IT Service Management & Incident Resolution System

**CS F213 / MAC F212 · Object Oriented Programming, Semester I, 2026-2027 · Group 67**
Repository: <https://github.com/kart1k1927/OOPS_PROJECT_67>

A web application managing the full lifecycle of an IT incident:
**Report → Classify → Prioritize → Assign → Investigate → Resolve → Verify → Close.**

Submission deadline: **22 November 2026** (report PDF plus a 15 to 20 minute demo video named
`67_OOP_S1_2025-2026_Project`).

## Run it

### 1. Install

```sh
python3 -m venv .venv && source .venv/bin/activate && pip install -r requirements.txt
```

### 2. Configure

```sh
cp .env.example .env
```

Fill in `SUPABASE_URL`, `SUPABASE_ANON_KEY` and `SUPABASE_SERVICE_ROLE_KEY`, then generate a session
secret:

```sh
python -c "import secrets; print('JWT_SECRET=\"' + secrets.token_urlsafe(48) + '\"')" >> .env
```

### 3. Apply the database schema

Supabase dashboard → SQL Editor → New query, and run these in order:

| File | What it does |
|---|---|
| `app/database/schema.sql` | Tables, indexes, RLS policies |
| `app/database/seed.sql` | 9 categories, 4 services, 4 SLA policies |
| `app/database/migrations/002_app_identity_and_lifecycle.sql` | **Required.** Application owned identity, the ACKNOWLEDGED and VERIFIED states, SLA precision fix, and removal of the two triggers whose logic moved to Python |

Every statement in 002 is guarded, so it is safe to run twice.

### 4. Seed demo data

```sh
PYTHONPATH=. .venv/bin/python scripts/seed_demo.py
```

Creates 9 people and about 34 incidents spread across the lifecycle, aged over the past five days so
the analytics and SLA screens have something real in them. Everyone's password is `campus2026`.

### 5. Start

```sh
.venv/bin/uvicorn app.main:app --reload
```

- Application: <http://127.0.0.1:8000>
- API documentation: <http://127.0.0.1:8000/docs>
- Health and configuration: <http://127.0.0.1:8000/health>

Sign in as `admin@bits.ac.in`, `priya@bits.ac.in` or `ravi@bits.ac.in`.

### No database keys?

```sh
PYTHONPATH=. .venv/bin/python scripts/demo_server.py
```

Runs the entire application against in-memory repositories with demo data already loaded. Everything
works except persistence. This is possible because the services depend on repository interfaces
rather than on Supabase, which is the practical argument for the Repository pattern.

### Tests

```sh
PYTHONPATH=. .venv/bin/python -m pytest tests/ -q
```

68 tests. No database, no keys, no network.

## Deploying it

### Why not Vercel

Vercel runs serverless functions. Three parts of this application need a process that stays alive
between requests, so it is the wrong shape:

| What | Where | What breaks |
|---|---|---|
| SLA monitor | `app/main.py` `_sla_monitor()` | An asyncio task sweeping every 60 seconds. A function is killed after the response, so breach flags and escalations stop updating. |
| Runtime strategy switching | `app/services/settings_service.py` | `SystemSettings` lives in process. Switching strategy would change one instance while the next request hits another. |
| Round robin rotation | `app/domain/assignment.py` | An `itertools.count()` in memory. Every cold start resets it to the first technician. |

FastAPI can be hosted on Vercel through an ASGI adapter, but only after removing the monitor and
moving the settings into the database. That is work in exchange for a worse demo.

### Render, free tier

`render.yaml` is in the repository, so this is four steps.

1. Push the repository to GitHub.
2. Render dashboard, **New**, **Blueprint**, pick the repository. It reads `render.yaml`.
3. Set three environment variables in the dashboard when prompted: `SUPABASE_URL`,
   `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`. `JWT_SECRET` is generated by Render, so nobody
   has to invent one, and no secret is ever committed.
4. Deploy. The URL is `https://iitsm.onrender.com` or whatever name you pick.

Health check is `/health`, which reports the database connection, the active strategies and the
registered notification channels.

**One worker, deliberately.** Each worker would run its own SLA sweep, so two workers means two
notifications for every breach.

**The free tier sleeps after 15 minutes of inactivity** and takes roughly a minute to wake. For a
recorded demo, open the link and let it wake before you start recording. The overview page has a
**Run SLA check now** button so breaches can be refreshed on cue rather than waiting for the next
60 second tick.

### Anywhere else

`Dockerfile` covers Fly.io, Koyeb, Cloud Run, Hugging Face Spaces or a campus VM. `Procfile` covers
anything Heroku shaped. Both use the same single-worker start command and the same health check.

### Before you deploy

- The three SQL files must have been run against the Supabase project (see above). Deployment does
  not create tables.
- `.env` is gitignored and must stay that way. The service role key bypasses row level security.
- Run `scripts/seed_demo.py` once against the deployed project, otherwise an evaluator opening the
  link sees empty tables.

## How it is built

```
app/
├── main.py                 app wiring, exception handlers, SLA background task
├── core/
│   ├── config.py           settings, validated at startup
│   ├── security.py         PBKDF2 password hashing, JWT sessions
│   └── exceptions.py       ITSMError hierarchy, each carrying its HTTP status
├── domain/                 pure Python, no framework imports, no I/O
│   ├── enums.py            Role, Status, Priority, Impact, Urgency, SLAState
│   ├── users.py            User (abstract) -> Employee / Technician / Administrator
│   ├── incident.py         the Incident aggregate
│   ├── states.py           State pattern: one class per status
│   ├── priority.py         Strategy: weighted and matrix
│   ├── assignment.py       Strategy: skill, load, round robin, experience
│   ├── sla.py              SLATracker, composed into every incident
│   ├── catalog.py          ITService, Category, SLAPolicy
│   ├── events.py           Observer: EventBus, IncidentEvent
│   ├── actions.py          what a role may do to an incident right now
│   └── factories.py        Factory: UserFactory, IncidentFactory, NotificationFactory
├── repositories/           Repository pattern
│   ├── base.py             the abstract interfaces and IncidentQuery
│   ├── mappers.py          row to object, the only place column names appear
│   ├── supabase_repo.py    production implementation
│   └── memory_repo.py      in-memory implementation, used by the tests
├── services/
│   ├── incident_service.py use case orchestration, the single authorised write path
│   ├── notification_service.py  three channels behind one abstraction, plus observers
│   ├── sla_service.py      continuous monitoring, breach detection, escalation
│   ├── reporting_service.py analytics for the admin screens
│   ├── auth_service.py     registration and sign in
│   ├── settings_service.py runtime strategy switching
│   ├── container.py        composition root
│   └── intelligence/       the automated features
├── api/
│   ├── deps.py             current user, role gates
│   ├── presenters.py       formatting helpers for the templates
│   └── routers/            pages, auth, incidents, technicians, admin
├── templates/              Jinja2, server rendered
├── static/css/             tokens, components, layout
└── database/               schema, seed, migrations
```

**Business logic lives in `domain/` and `services/`, never in routers and never in SQL.** The two
triggers that originally did assignment and SLA arithmetic in plpgsql are dropped by migration 002.
Their functions are left in the database so the decision can be discussed in the viva.

## Design patterns

Five, where the brief asks for two.

| Pattern | Where | Why it is there |
|---|---|---|
| **State** | `domain/states.py` | One class per status, each declaring its legal successors. `OPEN -> CLOSED` raises `InvalidStateTransitionError` and says what is allowed instead. Adding a state means adding a class. |
| **Strategy** | `domain/assignment.py`, `domain/priority.py` | Four assignment strategies and two priority algorithms, interchangeable at runtime from the admin settings page. Nothing above them names a concrete class. |
| **Observer** | `domain/events.py`, observers in `notification_service.py` | An incident does not know notifications or auditing exist. It raises an event; listeners react. An observer that throws is logged and skipped, never allowed to lose the incident. |
| **Repository** | `repositories/` | Two implementations of the same interfaces. The test suite swaps in the in-memory one and gets the real domain logic with no infrastructure. |
| **Factory** | `domain/factories.py` | `UserFactory` picks the right `User` subclass from a role string. `IncidentFactory` guarantees an incident arrives with its priority calculated and its SLA deadlines already derived. |

### Object oriented requirements, and where to find each

| Requirement | Where |
|---|---|
| Encapsulation | `Incident` has no public setters. Status changes only through `transition_to`, priority only through `apply_priority`, which also recalculates the SLA so the two cannot drift apart. |
| Abstraction | `AssignmentStrategy`, `PriorityStrategy`, `IncidentState`, `Repository`, `NotificationChannel`, `Observer` are all abstract base classes. |
| Inheritance | `User -> Employee / Technician / Administrator`, where the "is-a" test genuinely holds and the subclasses differ in behaviour, not just data. |
| Polymorphism | `home_route()`, `can_view()` and `available_actions()` are answered differently per role. The API and templates call those three methods and never check `if role ==`. |
| Interfaces | The abstract classes above define contracts that multiple concrete classes satisfy. |
| Composition | An `Incident` has-a `SLATracker`. A `Technician` has-a skill set and a workload. |
| Association / aggregation | An incident references an `ITService` and a `Category` that outlive it, and holds a list of `IncidentUpdate` that does not. |
| Exception handling | `ITSMError` and 17 subclasses, each carrying its own HTTP status, translated by one handler in `main.py`. |
| Collections | Frozen sets for transition tables, enums for closed value sets, a dataclass per value object, dictionaries for the strategy registries. |

## Features

### Incident lifecycle

```
OPEN -> CLASSIFIED -> ASSIGNED -> ACKNOWLEDGED -> IN_PROGRESS -> RESOLVED -> VERIFIED -> CLOSED
                                        |              |             |
                                        +--> PENDING <--+             +--> IN_PROGRESS (reopened)
```

Illegal transitions are refused with a message that says what is possible from here. The admin
settings page renders the whole table from `transition_graph()`, so the documentation cannot drift
from the code.

### Priority

`impact × urgency × business_criticality`, plus a bump for the number of people affected, mapped to
P1 to P4 by score. The report form shows the calculation live as the fields change, which is the
Strategy pattern visible on screen rather than claimed in a report.

### Assignment

Four strategies, swappable at runtime: skill based (default), load balanced, round robin and
experience weighted. All of them filter on availability first, so a technician who is inactive or at
their workload ceiling is never selected, whatever the ranking rule says.

### SLA

Deadlines derive from the policy for the incident's priority. A background task sweeps every 60
seconds to refresh breach flags, warn once when an incident crosses 75 percent of its window, and
hand anything overdue to the escalation engine. An administrator can force a sweep from the overview
page, which is how to demonstrate a breach on cue.

### Notifications

Three channels behind one `NotificationChannel` abstraction: in-app (real), email and SMS (both
simulated, writing to `logs/outbox.log`). Routing is by priority, so a P1 breach reaches everything
and a P4 comment reaches only the bell menu.

### Intelligent and automated features

| Feature | How |
|---|---|
| Duplicate detection | Blended Jaccard and overlap similarity over tokenised title and description, bonuses for the same service and category, 48 hour window. Flags rather than blocks. |
| Incident correlation | Groups open incidents by affected service, so six reports of one outage read as one cluster. |
| Automatic categorization | Weighted keyword scoring over the nine categories, with the matched terms shown so the reporter can override it. |
| Automatic escalation | Technician, senior technician, administrator, IT management, driven off the escalation deadline. Widens who is told, never reassigns. |
| SLA risk prediction | Five weighted signals producing a 0 to 100 score with the reasoning attached. |
| Technician recommendation | Ranks on skills, spare capacity, experience and track record with the affected service, with reasons. |
| Suggested resolutions | Surfaces what fixed similar incidents before, shown to the technician on the work view. |

All rule based. The brief says AI and ML are optional, and a deterministic algorithm is something
the team can defend line by line in a viva.

### Search and filtering

Nine criteria that compose: free text, incident reference, status, priority, category, service,
technician, SLA state, date range, plus open-only and unassigned-only toggles and four sort orders.
The brief asks for five.

## Security

| Concern | Approach |
|---|---|
| Passwords | PBKDF2-HMAC-SHA256, 390,000 iterations, per-user salt, parameters stored with the hash. Never logged, never returned by an endpoint, never put in a template context. |
| Sessions | Signed JWT in an HttpOnly, SameSite=Lax cookie, so page scripts cannot read the token. |
| Authorisation | Two layers. A role gate on the endpoint, then per incident checks inside the service through `User.require_action`, which consults both the role and the state machine. A forged POST for an action the interface does not offer is refused with 403 (see `tests/test_api.py::test_52`). |
| Enumeration | An unknown email and a wrong password return the identical message. |
| Input validation | In the domain objects, so it cannot be bypassed by calling a service directly. |
| Database | RLS stays enabled as a second line. The backend authorises in Python, which is where the object model can express it. |

## Interface

`docs/design-system.md` is the full specification. In short: an operations console rather than a
product page. Colour means status and nothing else, so the only saturated colour on screen is a
priority, an SLA state or a destructive action. Separation comes from 1px hairlines, not shadows.
Identifiers, timestamps, durations and SLA countdowns are set in IBM Plex Mono with tabular
numerals; prose is IBM Plex Sans.

Two screens are worth demonstrating specifically:

- **The report form** shows the priority calculation updating live, with the formula written out.
- **The technician work view** shows only the actions the state machine currently permits. A
  technician never sees a greyed out button, they see fewer buttons.

Responsive scope is deliberate: the three employee screens work on a phone, because that is the role
that files a ticket while standing in front of a broken printer. The technician and administrator
screens target 1024 and up and are usable but not optimised below that.
